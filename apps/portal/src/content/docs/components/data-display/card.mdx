The `Card` component provides a flexible container for displaying content within a card layout. It's composed from four parts — `Root`, `Image`, `Title`, and `Content` — and supports various configurations such as sizes, orientations, and the position of the image relative to the content.

## Anatomy

`Card` is a compound component: a `Card.Root` container that you fill with any combination of `Card.Image`, `Card.Title`, and `Card.Content`.

```typescript jsx
<Card.Root>
  <Card.Image src="…" alt="…" />          {/* optional */}
  <Card.Title>Title</Card.Title>          {/* optional */}
  <Card.Content>Body text</Card.Content>  {/* optional */}
</Card.Root>
```

- **Root** — a plain `<div>` that lays out the card. It picks the **first** `Card.Image` child out of the children and renders it as the card's image, then wraps everything else in an internal content wrapper. `size`, `orientation`, `position`, `selected`, `disabled`, and `interactive` are all styling variants applied here.
- **Image** — an `<img>`. Pass `width`/`height` as numbers (rendered as pixels) or CSS strings. Its `alt` comes straight from the `alt` you pass.
- **Title** — a heading, rendered as `<h3>` by default. Use `as` to set the correct level for the surrounding document outline (`h1`–`h6`).
- **Content** — a `<div>` for the card's body text or other content.

A few things to know about how Root arranges its children:

- Only the **first** `Card.Image` is treated as the image; any additional images fall into the content wrapper alongside the title and content.
- The image always renders **before** the content wrapper in the DOM. The visual placement (above/below, left/right) is controlled by `orientation` and `position` through CSS — not by where you put `Card.Image` in the source.
- All three children are optional — a card can be image-only, title-only, content-only, or any mix.

## Best practices

{/* TODO: editorial — please review against product guidance. */}

**Do**

- Keep each card focused on a single subject — one image, one title, one short block of content.
- Set `Card.Title`'s `as` prop so the heading level fits the page's outline, rather than always leaving it at `h3`.
- Use `orientation`/`position` for layout instead of reordering children — the DOM order stays fixed regardless.
- Give every meaningful `Card.Image` a descriptive `alt`, and use `alt=""` for purely decorative images.

**Don't**

- Don't rely on `selected`, `disabled`, or `interactive` to make the card behave like a control — they're visual styles only (see the accessibility notes).
- Don't put more than one `Card.Image` in a card expecting both to appear as images — only the first is placed as the image.
- Don't pack long-form content or many actions into a card; it's a summary surface, not a page.

## Content

{/* TODO: editorial — please review against product guidance. */}

- Write titles as short, scannable labels (a name or subject), not full sentences.
- Keep content to a sentence or two that supports the title; link out for detail rather than expanding the card.
- Use sentence case for both title and content.

## Accessibility

`Card` is a presentational container. `Card.Root` renders a plain `<div>` with no ARIA role, and its variant props change appearance only — they don't add behavior or semantics.

### Labeling

- `Card.Title` renders a real heading (`<h3>` by default). Set `as` so the level is correct in context, since a wrong heading level disrupts the document outline for screen-reader users.
- `Card.Image` needs an accessible name: pass a descriptive `alt` for informative images, or `alt=""` to mark it decorative so it's skipped. If you omit `alt` entirely, the image has no `alt` attribute and assistive tech may announce the file name.

### Focus & states

- Root, Image, Title, and Content all forward the standard HTML attributes you pass them onto their rendered elements, so you can add `id`, `aria-*`, `role`, etc. yourself when a card needs richer semantics.
- The card itself is not focusable and has no keyboard handling. Any interactivity has to come from focusable elements you place inside it (a link, a button).

### Known limitations

- **`interactive` is visual only.** It applies a hover/interaction style but doesn't make the card focusable, doesn't give it a `button`/`link` role, and adds no keyboard handling. If the whole card should be clickable, nest a real interactive element (e.g. a link that covers the card) and manage focus and keyboard activation yourself.
- **`selected` and `disabled` don't reach assistive tech.** They toggle styling classes but set no `aria-selected` or `aria-disabled`, and `disabled` does not actually prevent interaction with anything inside the card. Convey those states with the appropriate ARIA attributes (and real disabling) on the interactive element, not with the card variant alone.
