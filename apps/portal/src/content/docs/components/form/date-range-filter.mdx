The `DateRangeFilter` is a filter field type (`FilterFieldTypes.DateRange`) in the filters system. It presents a dropdown with grouped preset date ranges (Recommended, Relative dates, Calendar months) and a "Select custom range" option. Clicking "Select custom range" reveals a two-month calendar alongside the preset list for picking an arbitrary date range.

`FilterFieldTypes.DateRange` integrates the standalone [`DateRangePicker`](./date-range-picker/) with the filters system. It uses the same controlled semantic value, presets, timezone behavior, and optional capabilities while adding filter trigger and remove-filter behavior.

## Installation

```typescript jsx
import { useState } from 'react'
import {
  dateRangeValueParser,
  FilterField,
  FilterFieldTypes,
  type SemanticDateRangeValue,
} from '@harnessio/ui/components'

export const Filters = () => {
  const [value, setValue] = useState<SemanticDateRangeValue>()

  return (
    <FilterField
      filterOption={{
        type: FilterFieldTypes.DateRange,
        label: 'Timeframe',
        value: 'timeframe',
        parser: dateRangeValueParser,
        filterFieldConfig: {
          defaultTimeZone: 'UTC',
          weekStartsOn: 1,
        },
      }}
      removeFilter={() => setValue(undefined)}
      shouldOpenFilter={false}
      onChange={setValue}
      value={value}
    />
  )
}
```

The controlled value is the same semantic union used by the standalone picker:

- `relative` stores a live past or future rolling window.
- `calendar` stores a named period such as `last_week` or `next_month`.
- `absolute` stores fixed civil dates and optional times.

The browser's own timezone is the default (falling back to UTC only if it can't be detected); set `defaultTimeZone` in `filterFieldConfig` to pin a fixed zone instead. The selected IANA timezone persists on every semantic value so reloading a URL or saved filter preserves local calendar boundaries. `resolveDateRange` converts the value to inclusive `from` and exclusive `to` UTC instants (`[from, to)`) when the product constructs its query.

## Configure picker capabilities

```typescript jsx
const filterFieldConfig = {
  allowFuture: true,
  enableOffset: true,
  enableExclusions: true,
  defaultTimeZone: "America/New_York",
  weekStartsOn: 1,
};
```

- Future dates are enabled by default. Set `allowFuture: false` to opt out, or pass additional constraints through `calendarProps`.
- Fixed ranges always show editable full-day endpoint times. Rolling and calendar values retain derived boundaries.
- Offset and exclusion controls are hidden unless `enableOffset` or `enableExclusions` is set. They appear only in Rolling and commit with the range through the same Apply action. Their semantic adjustment is mutually exclusive, and offsets additionally require a past/Last direction.
- After a complete fixed range, the next date click resets the range and starts a new selection.

## URL and saved-filter persistence

Assign `dateRangeValueParser` to the filter option's `parser`. Its versioned format round-trips semantic kind, timezone, absolute dates and times, and relative adjustments. The parser throws for invalid persisted input; use `parseDateRangeValue` directly when a non-throwing `undefined` result is preferable.

Legacy `{ from, to, preset? }` values and `{ label, value, group, getRange }` presets remain accepted to avoid breaking existing filters, but both forms are deprecated. Legacy snapshots cannot fully preserve live intent. Prefer semantic values and presets shaped as `{ id, label, group, value }`.

## Custom semantic presets

```typescript jsx
const presets = [
  {
    id: "next-14-days",
    label: "Next 14 days",
    group: "recommended",
    value: {
      kind: "relative",
      direction: "future",
      amount: 14,
      unit: "day",
      timeZone: "UTC",
    },
  },
];

const filterFieldConfig = { presets };
```

Preset values are semantic and therefore stay live. The picker applies its currently selected timezone when a user chooses a preset.

## Anatomy

The date range filter isn't a standalone component — it's a `FilterField` configured with `type: FilterFieldTypes.DateRange`. That field renders a trigger button that opens a dropdown of preset ranges:

```tsx
<FilterField
  filterOption={{
    type: FilterFieldTypes.DateRange,
    label: "Timeframe",
    value: "timeframe",
    filterFieldConfig: {
      presets, // optional — defaults to a built-in set
      showCustomRange: true, // optional — defaults to true
    },
  }}
  value={value}
  onChange={setValue}
  removeFilter={() => setValue(undefined)}
  shouldOpenFilter={false}
/>
```

- **Trigger** — a button showing the filter's `label`; once a range is chosen it appends the formatted range (e.g. `Timeframe: Jan 3 – Jan 10`) and carries a tooltip with the same text, plus a chevron.
- **Dropdown** — opening the trigger reveals the preset list. Presets are grouped into **Recommended**, **Relative dates**, and **Calendar months** sections (only groups that have presets are shown), and each item shows its label alongside the concrete dates it resolves to.
- **Select custom range** — when `showCustomRange` is left on, a highlighted "Select custom range" item sits below the recommended group; opening it reveals a two-month range calendar for picking arbitrary `from`/`to` dates.
- **Delete filter** — the dropdown header holds a trash button that removes the filter entirely (calls `removeFilter`).

If you don't pass `presets`, a default set is used (Last 7 Days, This Month, Last 30 Days, quarters, years, and so on).

## Best practices

{/* TODO: editorial — please review against product guidance. */}

**Do**

- Lead with the ranges people pick most and put them in the **Recommended** group so they're reachable first.
- Keep preset labels short and unambiguous ("Last 30 days", "This quarter") and let the resolved dates underneath supply the specifics.
- Turn off `showCustomRange` when an arbitrary range doesn't make sense for the data, so the menu stays focused on the presets that do.

**Don't**

- Don't overload a single filter with a long, ungrouped list of presets — use the three groups to give the list structure.
- Don't rely on the filter to validate business rules (e.g. a maximum span); enforce those where you consume the emitted range.

## Content

{/* TODO: editorial — please review against product guidance. */}

- Give the filter a `label` that names the thing being filtered ("Timeframe", "Created", "Period"), not the action.
- Write preset labels in sentence case and keep the vocabulary consistent across filters ("Last 7 days" everywhere, not "Past week" in one place).

## Accessibility

The trigger is a standard [Button](/components/actions/button/) and the menu is built on the [Dropdown Menu](/components/overlays/dropdown-menu/) primitive, so it inherits their semantics.

### Keyboard

- The trigger opens with **Enter** or **Space**. Inside the menu, **Arrow** keys move between preset items, **Enter** selects, and **Escape** closes and returns focus to the trigger.
- "Select custom range" opens a submenu; the calendar inside is keyboard-navigable (arrow keys between days, **Enter** to pick the start then the end of the range).

### Labeling

- The trigger reads out the filter `label` and, once set, the selected range. Each preset item announces its label together with the concrete dates it resolves to.
- The delete control in the dropdown header is icon-only but carries an accessible "Delete filter" label.

### Focus & states

- Focus is trapped within the open menu and returns to the trigger on close. The selected range is reflected in the calendar's highlighted days when you reopen "Select custom range".

### Known limitations

- **Selection is conveyed visually in the calendar.** The picked range shows through highlighted day cells; there's no separate textual announcement of the range as you build it in the calendar, so confirm the resulting range from the trigger label.
