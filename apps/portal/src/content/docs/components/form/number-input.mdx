The `NumberInput` component handles numeric input, providing options for styling via themes and sizes. It also offers options for adding stepper controls, captions, suffixes, tooltips, and error or warning text for the field.

  </Layout.Vertical>
`}
/>

### Theme

The `NumberInput` component accepts a `theme` prop, which defines the visual state of the input: either `success`, `warning`, or `danger`.

Passing a message to `error` forces the `danger` theme, and passing a message to `warning` forces the `warning` theme — these override any explicit `theme`.

<DocsPage.ComponentExample
  client:only
  code={`

      label="Success"
      theme="success"
      caption="Caption text"
    />

      id="error-input"

    />

## Anatomy

`NumberInput` is a native `<input type="number">` wrapped with a label, optional caption, and stepper controls.

```tsx
<NumberInput
  label="Quantity"
  min={0}
  max={100}
  step={1}
  defaultValue={1}
  onChange={(e) => handleChange(e.target.value)}
/>
```

- **Label** — associated with the input via `htmlFor`; add `optional`, `labelSuffix`, or `tooltipContent` / `tooltipProps` for extra affordances.
- **Input** — a real numeric input. `value` (controlled) or `defaultValue` (uncontrolled) sets the number; `onChange` is the native change handler, so read `event.target.value`.
- **Stepper controls** — up / down buttons rendered in the input's suffix that call the native step behavior by `step`. Hidden when `hideStepper` or `readOnly` is set.
- **Caption / message** — `error` shows first, then `warning`, then `caption` below the field (in horizontal orientation the caption moves up beside the label).

## Best practices

{/* TODO: editorial — please review against product guidance. */}

**Do**

- Set `min`, `max`, and `step` to match the real constraints of the value so the steppers and validation behave sensibly.
- Use `integerOnly` for counts and quantities that can't be fractional.
- Provide a `suffix` (e.g. a unit) or `caption` when the number's meaning isn't obvious from the label alone.

**Don't**

- Don't use `NumberInput` for values that aren't really numbers (phone numbers, IDs, codes) — use a text input so leading zeros and formatting are preserved.
- Don't rely on `integerOnly` alone to guarantee whole numbers on submit — validate the final value as well (see limitations).

## Content

{/* TODO: editorial — please review against product guidance. */}

- Label the input with the noun it captures ("Quantity", "Replicas"), not an instruction.
- Keep captions to a short constraint or hint ("Between 0 and 100").
- Put units in the `suffix` rather than the label when space allows.

## Accessibility

### Keyboard

- The input is a native numeric field: **Up / Down arrows** increment and decrement by `step` when the field is focused.
- The stepper buttons are intentionally removed from the tab order (`tabIndex={-1}`), so keyboard users step with the arrow keys rather than tabbing to the buttons.

### Labeling

- The label is tied to the input with `htmlFor`; when no `id` is supplied one is generated automatically so the association still holds.
- The increment / decrement buttons carry `aria-label`s ("Increment value" / "Decrement value").

### Focus & states

- `disabled`, `readOnly`, and `optional` are supported. When `readOnly` is set the steppers are hidden along with `hideStepper`.
- `inputMode` is set (`numeric` when `integerOnly`, otherwise `decimal`) so mobile keyboards show the right keys.

### Known limitations

- **`integerOnly` doesn't cover paste.** It blocks a typed decimal point but does not sanitize a pasted decimal value, so validate the committed value if whole numbers are required.
