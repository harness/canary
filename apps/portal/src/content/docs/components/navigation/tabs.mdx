The `Tabs` component organizes content into multiple panels, each associated with a tab trigger. It comes in two modes: regular tabs that show and hide panels, and navigation tabs (`Tabs.NavRoot`) that integrate with your router.

It is composed from `Tabs.Root`, `Tabs.NavRoot`, `Tabs.List`, `Tabs.Trigger`, and `Tabs.Content`, so you assemble exactly the structure you need.

        <Tabs.Trigger value="tab3">Tab 3</Tabs.Trigger>

## Anatomy

All parts of the `Tabs` component can be imported and composed as required. Regular tabs pair a `List` of triggers with matching `Content` panels; navigation tabs use `NavRoot` and drive routing from each trigger, so panels are usually rendered by the router instead.

```tsx
// Regular tabs
<Tabs.Root>
  <Tabs.List>
    <Tabs.Trigger />
  </Tabs.List>
  <Tabs.Content />
</Tabs.Root>

// Navigation tabs
<Tabs.NavRoot>
  <Tabs.List>
    <Tabs.Trigger />
  </Tabs.List>
</Tabs.NavRoot>
```

- `Tabs.List` holds the triggers and carries the visual `variant`. It automatically enables overflow scrolling with fade indicators and scrolls the active tab into view.
- `Tabs.Trigger` is a single tab. It inherits its variant from the `List`, and can show an `icon`, a `logo`, a `counter` badge, or fully custom `children`.
- `Tabs.Content` is the panel shown for the active tab in regular tabs. In navigation tabs it renders as a plain container whose visibility you control through routing.

## Best practices

**Do**

- Give every trigger a unique `value`, and provide either a `defaultValue` or a controlled `value` so a tab is selected on first render.
- Use descriptive trigger text so the tabs are understandable on their own.
- Reach for `Tabs.NavRoot` when tabs represent different routes in your application.
- Let the component handle overflow — many tabs will scroll horizontally with fade indicators rather than wrapping.

**Don't**

- Don't put both an `icon` and a `logo` on the same trigger; they are mutually exclusive.
- Don't set `variant` per trigger to differ within one list — apply it once on the `List` so the group stays consistent.

## Accessibility

### Keyboard

- In regular tabs, arrow keys move between triggers with a roving tabindex: <kbd>←</kbd>/<kbd>→</kbd> for horizontal and <kbd>↑</kbd>/<kbd>↓</kbd> for vertical, with <kbd>Home</kbd>/<kbd>End</kbd> jumping to the first/last tab.
- Disabled triggers are skipped during keyboard navigation.

### Labeling

- Regular tabs render `role="tablist"` with `role="tab"` triggers and a matching `tabpanel`, wired up by the underlying primitive.
- Navigation tabs render the `List` as a `<nav>` element with each trigger as a link, so they're announced as navigation.
- Use clear, human-readable trigger text; for icon- or logo-only triggers, make sure the trigger still has an accessible name.

### Focus & states

- The active content panel is given `tabIndex={-1}` so focus can move into it programmatically.
- `disabled` triggers can't be focused or activated. In navigation mode a disabled trigger gets `aria-disabled` and its navigation is prevented.

### Known limitations

- `Tabs.NavRoot` is a context provider that only uses its `children` — `value`, `onValueChange`, `defaultValue`, `orientation`, and `className` passed to it are ignored. Drive the active tab from the current route through each `Trigger`.
- For navigation tabs, `aria-current` on the active tab comes from the router's `NavLink`, so wire up your router (e.g. react-router) for it to appear.
