The `Tooltip` component surfaces additional information for an element in a small overlay that appears on hover or focus. It supports a title, a scrollable body, a fixed footer, an arrow, and positioning on any side. Every `Tooltip` must have a `TooltipProvider` ancestor — typically wrapped around the entire app.

<DocsPage.ComponentExample
  client:only
  code={`<TooltipProvider>
    <div className="flex justify-center">
        <Tooltip
            content="Tooltips provide helpful context and information"
        >
            <Button variant="secondary">Hover me</Button>
        </Tooltip>
    </div>
</TooltipProvider>`}
/>

## Installation

```tsx
import { Tooltip, TooltipProvider } from "@harnessio/ui/components";

// TooltipProvider typically wraps the entire app.
<TooltipProvider>
  <Tooltip title="Title" content={<p>This is a tooltip</p>}>
    <Button variant="secondary">Hover me</Button>
  </Tooltip>
</TooltipProvider>;
```

## Anatomy

A `Tooltip` wraps a single trigger element and renders its overlay in a portal.

- `TooltipProvider` must sit above every tooltip — usually once at the app root. It shares delay and hover behaviour across the tooltips beneath it.
- `Tooltip` renders its `children` as the trigger (via `asChild`), so the child must be a single focusable element that forwards its props and ref.
- The overlay is portaled and holds up to three regions: an optional `title`, the scrollable `content` body, and an optional `footer` that stays fixed while the body scrolls.
- An arrow points at the trigger unless `hideArrow` is set.

<Aside type="note">
  The tooltip surface is always dark — including nested content — regardless of
  whether the app is in light or dark mode. The color and contrast variants from
  the current theme are preserved (for example `light-pro-high` renders as
  `dark-pro-high`). The drop shadow uses the lighter elevation (`--cn-shadow-1`)
  so it does not pick up the dark-mode black halo when forced dark over a light
  page.
</Aside>

## The `withTooltip` HOC

`withTooltip` adds tooltip support to any component. For it to work, the wrapped component must use `forwardRef` and spread its props, so the ref and trigger wiring reach the underlying element.

```tsx
import { withTooltip } from "@harnessio/ui/components";

const CompWithTooltip = withTooltip(YourComp);

// The wrapped component gains an optional `tooltipProps` object
// (every Tooltip prop except `children`). When omitted, no tooltip renders.
<CompWithTooltip tooltipProps={{ content: "Helpful context" }} />;
```

## Best practices

{/* TODO: editorial — please review against product guidance. */}

**Do**

- Keep tooltip content short and supplementary — a tooltip is context, not essential information.
- Attach the tooltip to a focusable trigger so keyboard and screen-reader users can reach it.
- Use `title` for a short label and `content` for the detail; reach for `footer` when a persistent action or link should stay visible as the body scrolls.

**Don't**

- Don't put essential information or the only copy of an action inside a tooltip — it isn't visible at a glance and may be missed.
- Don't wrap a non-interactive or non-focusable element as the trigger; the tooltip then can't be opened by keyboard.
- Don't rely on rich markup in `title` — it only accepts a string. Use `content` for anything richer.

## Accessibility

### Keyboard

- Focusing the trigger opens the tooltip; <kbd>Escape</kbd> closes it.
- Hovering the trigger opens the tooltip after the `delay`; moving the pointer away closes it.

### Labeling & semantics

- The trigger is associated with the overlay via `aria-describedby`, so assistive tech announces the tooltip as a description of the trigger.
- Because `children` becomes the trigger (`asChild`), pass a single focusable element that forwards props and ref — otherwise the accessibility wiring can't attach.
