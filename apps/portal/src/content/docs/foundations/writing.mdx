## Voice & tone

_(Updated 2026-09-15 with Aaron's adopted UI writing decisions, based on Cloudscape Design System writing patterns — these are settled decisions, not proposals.)_

- Use sentence case, but continue to capitalize proper nouns and brand names correctly in context. Use present-tense verbs and active voice.
- **Speak to the user directly, not about them.** Prefer "you" over "the user": _"You can configure a webhook"_ rather than _"The user can configure a webhook."_
- **Use end punctuation** in body copy — with two exceptions: headers and buttons never take a period, exclamation point, or colon (a question mark is fine for a genuine yes/no confirmation header, as in the Buttons example below). Don't use exclamation points anywhere.
- **Don't use:** "please," "thank you," ellipses (`...`), the ampersand (`&`), "e.g.," "i.e.," or "etc." — spell things out instead. (_No: "Please enter a name for your pipeline." Yes: "Enter a name for your pipeline."_)
- **Write for a global audience.** Avoid humor, idioms, and culturally-specific references; avoid unnecessary jargon; use plain language. Copy is American English by convention.
- **Avoid directional language.** Use _previous_ / _following_, not _above_ / _below_ — content position can shift across viewports and screen sizes.
- **Use device-independent language.** Use _choose_ or _select_, not _click_ — not every input is a mouse.

## UI copy: tooltips & form fields

**Standard: every user-editable form field must have a tooltip.** Structural elements (section headers, layout containers) don't need one. Tooltip copy should be terse, clear, specific, and actionable — explain one thing well rather than everything about the field.

Writing principles for tooltip copy:

| Principle | Guidance |
|---|---|
| Universal | Applies the same rule everywhere a tooltip appears — don't special-case wording per surface. |
| Terse | Say the minimum needed to unblock the user at the point of configuration. |
| Clear | No jargon or ambiguity — a reader unfamiliar with the feature should still understand the field. |
| Specific | Name the actual behavior or value, not a vague generality. |
| Actionable | Tell the user what to do or what will happen, not just what the field "means." |
| Direct | Lead with the important part of the sentence; don't bury it in a subordinate clause. |
| Safe | Never imply a destructive or irreversible action is casual — flag consequences plainly. |

- **Name Harness explicitly** when describing product behavior (for example, "Harness runs this step on the delegate," not just "runs on the delegate").
- **Coverage rule** — a good tooltip explains, as relevant: what the field controls, where its value is used/sourced, what happens if it's left at its default, and any security/permissions implication.
- **Avoid:** restating the field's label back to the user; explaining implementation detail the user doesn't need to act on; a tooltip so long it needs its own scrollbar; vague filler like "Configure this setting" with no specifics.

Core drawer flows expected to have full tooltip coverage: pipelines/stages, CI/CD steps, services/environments/infrastructure, connectors, secrets, users/groups, roles, service accounts, and resource groups.

## UI writing conventions

_Adopted decisions (2026-09-15) for form fields, errors, links, buttons, and empty states — based on Cloudscape Design System writing patterns. These resolve most of the open XD-132 gaps that used to sit below (see Open gaps)._

**Form field labels**

- Sentence case, not title case.
- Clear, concise, consistent — guide the user across the form.
- Maximum three words; no articles ("a," "an," "the").
- No terminal punctuation.

**Form field descriptions**

- Sentence case, not title case. Descriptions are optional but usually worth including — they help the user understand what to enter.
- Place above the related field, not below. Constraints (e.g. alphanumeric restrictions) go below the field instead.
- Keep brief; active voice.
- End punctuation required, except when the description ends in an external-link icon (no period after the icon).
- Don't state the obvious (for example, "Enter a description").

**Error text** _(follows the Cloudscape error-message pattern)_

- **Required field:** "[Label descriptor] [label type] is required."
- **Invalid format:** "Enter a valid [label descriptor] [label type]." (for example, "Enter a valid email address." or "Enter a valid phone number.")
- **Doesn't match:** one short sentence stating what doesn't match; add a second sentence with clear next steps only if needed.
- **Character requirements:** put character-count requirements in the field's constraint text, not in a validation error. When a character-count error does trigger, it should say which constraint is unmet — for example: "The name has characters that aren't valid: #", "The name has too many characters. Character count: 120/50", or "The name has too few characters. Character count: 1/50".

**Link text** _(in-product links; complements the docs-writing "go to" convention below)_

- Never "click here" or similarly vague phrasing — give the user context for where the link goes.
- Match the destination's actual title where practical; a lengthy title can be abbreviated as long as the context stays clear, and can be simplified further if that clarifies the action.
- Every link gets an aria-label describing what it opens.

**Buttons**

- One or two words: an action verb ("Start," "Continue," "Open," "Add," "Create"); an action verb + proper noun/brand name, used sparingly ("Sync Git"); or an action verb + feature/item name ("Create pipeline," "Add stage").
- Let surrounding context (a section header, page title, and so on) carry clarity instead of padding the button label.
- A primary button's label should reflect the drawer/dialog's own primary action and match its header — not a generic "Yes." (e.g. header "Discard changes?" → button "Discard," not "Yes.")
- No terminal punctuation (period, exclamation point, question mark, colon); no articles ("Create template," not "Create a template").

**Empty states**

- _Heading_ — bold, no end punctuation. Empty state: e.g. "No input sets". Zero-results state: e.g. "No results".
- _Description_ — has end punctuation, not bold; explain why the state is empty and what to do next if needed; don't repeat the heading or button copy.
- _Action button_ — matches the corresponding table's button label and follows the button rules above. Empty-state examples: "Create pipeline," "Connect to GitHub," "View all projects." Zero-results state: always "Clear filter."

## Structure & formatting

- **Headings** — sentence case (capitalize only the first word and proper nouns), no ending punctuation, short noun or simple-present-tense verb phrases ("Create pipelines," not "Creating pipelines" or "How to create pipelines"). Every heading should orient the reader out of context — avoid vague headings like "Explore" in favor of "Explore dashboards." Don't skip heading levels, and don't open a section with a redundant "Introduction" heading.
- **Lists** — keep list items grammatically parallel; introduce a list with a sentence that sets it up; use a numbered list only when order or step sequence genuinely matters, otherwise use bullets. Use the Oxford (serial) comma in running text.
- **Links** — use a "go to [destination]" convention and meaningful link text that describes the destination, never "click here."
- **UI elements in copy** — bold the name of a UI element being referenced (for example, "select **Save**"); avoid directional language like "the button on the left" since layout can shift; for an unlabeled icon-only control, reference it by its accessible/coded name rather than a visual description, for accessibility.
- **Code & YAML** — use code notation (monospace) for field names, YAML keys, and code snippets; never bold, italicize, or quote them instead.
